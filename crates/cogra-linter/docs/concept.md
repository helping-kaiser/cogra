# The Corpus Linter — Concept

_Phase 1 of the standard engineering process: concept. Review closes this phase; the design candidate follows._

This document is the concept for `crates/cogra-linter`: one Rust binary that walks the corpus — Markdown prose and compiled-platform source — and mechanically discharges the checkable obligations of the four adopted discipline documents, the label calculus, the kind registry, the identity adjudication procedure, and the interchange conventions. It states why the linter must exist, who consumes its findings, what it must do — every requirement traced to the discipline clause, architecture decision, or adoption datum that demands it — what it will not do, how it will be verified, and what the phases ahead look like. It decides nothing the architecture has already decided: that document is the ratified design, this one sits below it and cites it. Where the concept found a gap, a stale measurement, or a contradiction, it is recorded in (`sec:lint:questions`) for the review to rule on, not resolved here.

The document practices the labeling discipline: the label at each heading or environment head is that environment's mint; a parenthesized label in running text is a same-owner citation; material in fenced blocks and double-backtick spans is displayed without participating, which is where every token this document merely quotes sits. The document title mints nothing. Every label minted here has area `lint`. Under the owner partition this file belongs to `pkg.cogra-linter`, a different owner from the architecture document, whose area is `linter`; the area token is the one labeling choice the concept had to make and is open for ruling (`open:lint:area-token`). Imported citations use the prefixes registered in `corpus-adoption.toml`: `LBL` for the label calculus, `KND` for the kind registry, `IDN` for the identity adjudication procedure, `ICX` for the interchange conventions, and `ARCH` for the linter architecture.

## Purpose · `sec:lint:purpose`

**Formulation (Purpose)** · `formul:lint:purpose`

Four disciplines are adopted and none is enforced. Each was written to end in a gate — (`[LBL-gate:labels:implementation]`), (`[KND-gate:kinds:adoption]`), (`[IDN-gate:identity:implementation]`) — whose clauses are mechanical, and each closes that gate with the same sentence: it is dischargeable from that document and the corpus's adoption data alone, no check consulting another document. A checker is therefore not one possible consumer of these documents but the discharge mechanism they were written for, and the calculus says as much of itself — the checker and the register generator are its only consumers (`[LBL-cav:labels:non-normativity]`). An adopted-but-unchecked discipline is worse than an unadopted one: citations dangle silently, registers go stale while still looking authoritative, and a corpus that cannot say what it means by a name has paid the discipline's cost without buying its benefit. The cost is already sunk and the drift already measurable — twenty-nine committed Markdown files carry label-shaped prose spans, ~119 occurrences among them are imported citations across five owners, and the docs trees carry dozens of same-owner citations that resolve nowhere (`rep:lint:first-corpus`). Two ruled inventory profiles cover 284 test functions and ~42 module definitions whose labels are derived, not authored, and which no hand can maintain or verify at that scale. The linter is what turns four essays into four enforced disciplines.

**Signature (Consumers)** · `sig:lint:consumers`

Four consumers, present and planned. The corpus authors, who receive located diagnostics as they write and whose renames the linter makes safe by breaking exactly what the rename broke (`[LBL-metathm:labels:warrant-lapse]`). Continuous integration, which runs the corpus-wide check as the calculus's gate requires and fails the build on findings, distinguishing findings from crashes by exit code (`[ARCH-req:linter:diagnostics-not-panics]`). The gates themselves, whose clauses the linter is the instrument of: the architecture's own gate closes on a citation check the finished linter runs over the document that specified it (`[ARCH-gate:linter:architecture-review]`), and the identity gate requires the corpus's full checks to pass leaving no uncommitted generated changes (`[IDN-gate:identity:implementation]`). And the generated registers the disciplines call for — the per-owner label registers of the test profile, the kind registry's headline counts, the acceptee's companion attestation register — which have a generator only when the linter has one (`[ARCH-rule:linter:register-freshness]`). No consumer outside this repository exists in v1; the disciplines are corpus-generic and the crate layout anticipates extraction, but a second corpus is not a v1 consumer (`[ARCH-dec:linter:crate-layout]`).

**Requirement (Nothing about the corpus in the binary)** · `req:lint:adoption-data-only`

The linter is generic over corpora and the configuration is this corpus's adoption. All seven parametric data of the calculus plus this corpus's own additions — the carrier's exclusions, the banned-token sets — live in one committed file, and changing any of them is a reviewed edit to that file rather than a code change (`[ARCH-sig:linter:adoption-data]`). The consequences are concrete and load-bearing: path rules are literal prefixes with no pattern dialect, honoring the no-regex decision even in configuration (`[ARCH-dec:linter:no-regex]`); the kind registry's classification tables are parsed from the registry document rather than transcribed (`[ARCH-dec:linter:registry-as-data]`); and a new package needs no code change and no decision, joining the prefix family by its derivation rule (`[LBL-sig:labels:owners]`).

**Requirement (Determinism and order independence)** · `req:lint:determinism`

Two runs over one tree emit one output: diagnostics sort by path, then byte offset, then rule identifier, and no verdict depends on traversal order (`[ARCH-req:linter:determinism]`). Determinism is not a nicety here but the precondition of the central mechanism — a register compared byte-exactly against its committed form is only meaningful if regeneration is deterministic (`[ARCH-rule:linter:register-freshness]`), and order independence is what the calculus proves of itself (`[LBL-metathm:labels:order-independence]`).

**Requirement (Failures are diagnostics)** · `req:lint:diagnostics`

Malformed input never panics the linter, and every failure is scoped exactly as the discipline scopes it: an unpaired backtick fails its block while the rest of the file resolves, an opening acute unclosed at a region's end fails there, an unreadable tree is a reported traversal failure, and a frontend parse error is a hard located diagnostic rather than a silently skipped region (`[ARCH-req:linter:diagnostics-not-panics]`), (`[LBL-judg:labels:participation]`), (`[LBL-cav:labels:coexistence]`). Scoped register generation ignores unrelated owners' defects while the corpus-wide check still validates everything.

**Requirement (Timing)** · `req:lint:timing`

Every run reports wall time per phase — pre-tokenize, harvest, resolve, judge, render — and the first measured full-corpus run sets the budget recorded beside the CI lane that invokes the linter; exceeding it thereafter is a finding, not a cost to absorb (`[ARCH-req:linter:timing]`).

**Requirement (Workspace discipline)** · `req:lint:workspace-discipline`

The crate obeys every standing repository rule — `cargo fmt`, `clippy -D warnings`, no `unwrap` in library code, `thiserror` and `anyhow` for the error surface, no SQL — and the three fixed constraints of the architecture, which are the decisions most easily eroded in implementation and are therefore restated as requirements rather than left as context: every in-memory graph is a petgraph type used directly, with filtered views where a restricted graph is wanted and free functions where a domain operation is (`[ARCH-dec:linter:petgraph-first-class]`), (`[ARCH-rem:linter:views-not-wrappers]`); no regular-expression engine appears on the analysis path, the one signed exception living inside the interchange crate and nowhere else (`[ARCH-dec:linter:no-regex]`), (`[ARCH-dec:linter:cddl-regexp-library]`); and analysis runs over syntax trees, raw bytes being consulted only where the AST hands back a span whose delimiter form the discipline needs, and in the pre-tokenizer pass (`[ARCH-dec:linter:ast-frontends]`). Dependencies are the architecture's (`[ARCH-tab:linter:dependencies]`), each verified against its own current documentation before the first line depends on it.

## Scope boundary · `sec:lint:scope`

**Convention (Out of scope)** · `conv:lint:out-of-scope`

Version 1 is a checker: it reports, and humans and later tooling repair (`[ARCH-formul:linter:charter]`). The single exception is not repair but regeneration — an explicit mode that rewrites a generated register in place, never invoked by the check (`[ARCH-rule:linter:register-freshness]`) — and it invents nothing: an authored label no author has chosen is an absence rather than an opening, met as a defect to surface (`[LBL-inv:labels:generated-compliance]`). The corpus's pending migrations are consequently not the linter's work: the sweep of ~1210 plain line comments and the ~42 module definitions owed an inner documentation comment are separate tasks, and the linter's contribution to both is the located diagnostic.

Frontends are sliced, and a language with no frontend has no scanned regions: Markdown and Rust are the first slice, the web frontend the second, Kotlin the third behind the precondition that a first-party grammar parses the whole Android corpus to zero error nodes, and LaTeX remains deferred (`[ARCH-conv:linter:web-frontend]`), (`[ARCH-dec:linter:kotlin-tree-sitter]`), (`[ARCH-open:linter:latex-frontend]`). SQL, GraphQL, TOML, Kotlin build scripts, shell, JSON, YAML and SVG get no frontend at all in v1; their files stay in the carrier and stay owned, carry no occurrences, and are vacuously in good standing (`[LBL-judg:labels:minting]`). The profile signature is likewise small on purpose: two Rust profiles, and no Markdown, TypeScript or Kotlin profile, because a profile whose frontend does not exist cannot compute a census and a half-computed census breaks the two-pass staging outright (`[LBL-inv:labels:two-pass]`). The designated typed-data classes and the citation-index designations are both empty and staged, so their checks have empty domains rather than absent implementations.

Three boundaries are not slicing but principle. The linter mints no digest and adds none, its freshness comparison being exact bytes and its no-identity outcome the recorded stop (`[IDN-case:identity:no-identity]`). Nothing outside the carrier is examined: the Layer 1 interface document sits outside the label graph entirely — no owner, no prefix, no scanned region — so nothing in it resolves and nothing in it can fail, until the upstream repository becomes public and joins as a citable owner. And the graph the linter builds is documentation, never semantic input: no compiler, build system, packager, or release tool consumes it, and no version of the software this corpus documents moves because a label was renamed (`[LBL-cav:labels:non-normativity]`).

**Convention (Clauses the linter does not discharge)** · `conv:lint:non-mechanical`

The gates are the acceptance criteria, but not every clause in them is a check, and the ones that are not belong to named authorities rather than to the binary. From the kind registry, the linter checks token distinctness, hybrid composition, catalogued pairs, and register currency; it does not judge that a token is one per *concept* or that a synonym class is convergent — those are the registry authority's editorial rulings — nor does it adjudicate attestation evidence, which the acceptee owns first-hand (`[KND-sig:kinds:acceptee]`), (`[KND-cav:kinds:attestation-limits]`). From the identity discipline the linter takes exactly one standing duty and one prohibition, as its charter says: exact byte comparison of committed generated publications, and no digest without a walked adjudication (`[ARCH-formul:linter:charter]`). The remainder of that gate — classifying every existing digest, recording admissions and stops, demonstrating that a recipe delivers its class's properties, binding evidence roles and release manifests — is a human review duty over the corpus, and the linter neither performs nor certifies it; the acyclicity check over an identity graph enters only when identity checking itself lands (`[ARCH-tab:linter:judgments-as-queries]`). From the label calculus, the final gate clause — that the corpus-wide check passes in continuous integration — is discharged by the CI lane, not by the binary that lane runs.

## Verification · `sec:lint:verification`

**Convention (Gates as acceptance criteria)** · `conv:lint:gates-as-acceptance`

The linter is accepted against the disciplines' own gates, clause by clause, and against nothing else: (`[LBL-gate:labels:implementation]`) in full, (`[KND-gate:kinds:adoption]`) and (`[IDN-gate:identity:implementation]`) in the parts (`conv:lint:non-mechanical`) leaves to it, and (`[ARCH-gate:linter:architecture-review]`) whose closing clause is a check the finished linter runs over the document that specified it. Each gate states that it is dischargeable from its own document and the corpus's adoption data alone, which fixes the shape of the acceptance suite: a clause is discharged by a test naming the clause, over this corpus's ruled adoption data, and no test consults a third document. The interchange conventions carry no gate of their own (`open:lint:interchange-gate`); their obligations are discharged by the sibling crate, whose audit and commissioning phases have closed, and the linter's duty toward them is delegation — R19 of (`tab:lint:functional`).

**Convention (Metatheorems as test obligations)** · `conv:lint:metatheorems-as-tests`

The label calculus proves four metatheorems about the system the linter implements, and each becomes an executable obligation rather than a paragraph. Order independence becomes a property test that shuffled traversal orders over one tree emit byte-identical output (`[LBL-metathm:labels:order-independence]`). No self-support becomes a test that an index row never sustains its own membership, and that removing a document's last body citation of a label stales the committed index (`[LBL-metathm:labels:no-self-support]`). Warrant lapse becomes a property test over transitions of a covered asset: renaming its identifier, changing its classification, moving it across packages, or removing it from the census dangles exactly the citations of the facet or boundary that moved, while moving it within its package lapses nothing (`[LBL-metathm:labels:warrant-lapse]`). Presentation invariance becomes a test that a migration re-forming occurrences while preserving every label value leaves every registry, every harvested set, and every hash computed from them unchanged (`[LBL-metathm:labels:presentation-invariance]`). The kind registry proves no metatheorems and instead asserts invariants over its own tables, which makes it its own first test corpus: it classifies its own heads, so parsing it and validating it are one exercise (`[ARCH-dec:linter:registry-as-data]`). The identity discipline prescribes no construction and its obligation is a policy assertion — that the crate contains no digest. The interchange metatheorems were already discharged as executable obligations inside the interchange crate and are not re-tested here. Property-test and fuzz sizing, and the budgets of (`req:lint:timing`), are the design candidate's to fix.

**Report (The first corpus)** · `rep:lint:first-corpus`

The four discipline documents are the truest acceptance test, because they practice the disciplines they define: each declares its own labeling convention in its preamble, mints one label per environment head, carries no environment numbering, and classifies its own heads by the registry. *The linter lints its own four discipline documents* is therefore the first honest milestone, followed by the architecture document and the interchange crate's phase artifacts — the material already written under the discipline.

The wider corpus is further from clean than the adoption data records, and the concept states the gap rather than discovering it in implementation. Measured 2026-08-25 by raw-text sweep, which can only over-count, participation being an AST fact this sweep cannot see: twenty-nine committed Markdown files outside the vendored Layer 1 document carry label-shaped single-backtick prose spans, where the adoption data records seven label-bearing files; imported citations numbered ~119 across five prefixes when this document joined them, against the 113 recorded five days earlier, the difference being the interchange audit and commissioning notes written since — a hand-kept measurement decaying inside a week, which is the purpose argument in miniature. In the three docs trees whose owners the adoption data records as carrying no label occurrences, 37 parenthesized label-shaped spans and roughly eight bare ones occur; their targets are names of the Layer 1 interface document, which is outside the carrier, so each parenthesized span is a same-owner citation resolving nowhere and each bare span would be read as a mint. Rust sources carry 88 label-shaped backtick spans inside documentation comments, where the code syntax is the acute — near-miss warnings rather than occurrences, and precisely the class the calculus asks the checker to warn on. Two bare label-shaped spans occur in the adoption notes themselves, a file whose preamble declares that its label-shaped references are written in double backticks throughout, and one of the two is the very span the surrounding sentence describes as a hazard. Two further spans, imported-citation-shaped and sitting inside fenced illustrations of the calculus, participate in nothing yet would be counted by any text sweep — the cleanest small demonstration of why the analysis is AST-based (`[ARCH-ansatz:linter:regex-scanning]`). What this measurement means for the corpus is a ruling, not a finding of this document (`open:lint:stray-occurrences`).

## Phases · `sec:lint:phases`

**Roadmap (Phase plan)** · `preview:lint:phase-plan`

The standard engineering process, instantiated for this crate — each phase closes on an explicit artifact, and the next does not start until the previous closes:

| --- | --- | --- |
| Concept | this document | review ruling |
| Design candidate | design.md: module map, the node and edge weight enums, error taxonomy, the first slice's public shape, dependency justifications, test plan sized | review ruling |

What still wants a design pass before code is the module map against the drawn boundaries (`[ARCH-dec:linter:crate-layout]`), the two weight enums whose variants the judgments query (`[ARCH-tab:linter:node-edge-vocabulary]`), and the public shape of the first slice. The audit phase is planned, not optional: on the previous run of this process the deferred hazards a design named came due there exactly as named.

## Open questions · `sec:lint:questions`

**Open question (The area token for this crate's artifacts)** · `open:lint:area-token`

The stance comes first: the kickoff keeps every label-shaped reference in double backticks so that planning state mints and cites nothing, while the interchange crate's committed phase artifacts participate in full; this document follows the phase artifacts, because it is one and is committed into the carrier, and its labels are therefore live. What the area token should be is the open part. This file belongs to the package owner `pkg.cogra-linter` under the ordered partition, while the architecture document is its own owner and mints in area `linter`. Two owners may mint one label text without collision, so reusing `linter` here is legal; the precedent argues against it. The interchange crate's phase artifacts deliberately took an area distinct from the conventions document they implement, renamed while the rename was still cheap, so that no two tokens invite the assumption that they name one thing. This document therefore mints in area `lint`, chosen for that reason and for no stronger one — it is one byte from the architecture's area, which is the objection to it. The alternatives are reusing `linter`, or a token further from it. The rename is cheap exactly now and never again.

**Open question (Stray occurrences in the docs trees)** · `open:lint:stray-occurrences`

The adoption data records the three docs trees as carrying no label occurrences and the corpus as having seven label-bearing files; the measurement in (`rep:lint:first-corpus`) finds twenty-nine files and dozens of occurrences, whose targets are names owned upstream and outside this corpus. Three readings are available and the choice is a ruling: the spans are references to an upstream owner that becomes citable when the Layer 1 repository is public, and are known findings until then; or they are defects to be reformed into displayed spans before the linter's first clean run; or the docs trees take promotion to owners of their own. The promotion condition the adoption rulings already state is arguably met — one of the two documents named for promotion the day it takes labels carries a bare label-shaped span today. Whichever reading stands, the adoption data's per-owner notes and its measurement table need the correction, and the file is outside this document's scope to edit.

**Open question (The kind registry's adoption data)** · `open:lint:kinds-adoption-data`

The adoption file instantiates the label calculus's seven parameters and this corpus's own additions, and instantiates none of the kind registry's: no acceptee is named, and no local extension set, evidence base, status map, register generator, or companion register exists. The registry's gate requires the adoption decision to name exactly one acceptee owning all five, and requires the companion register to be the current, deterministic, totally ordered output of that acceptee's evidence, presenting the homonym set and maintained only by regeneration (`[KND-sig:kinds:acceptee]`), (`[KND-req:kinds:attestation-register]`). The registry's own text supplies a default for the corpus it travels in — there, the registry authority is the acceptee and the edition evidence base is the whole of the evidence — but a default is not a recorded decision, and R14 of (`tab:lint:functional`) cannot be implemented against data that does not exist. Related and concrete: the registry's headline counts are declared a generated region maintained only by regeneration, yet no generator has ever produced them; whether the linter's regeneration mode is that generator, and what the committed counts are compared against until it is, wants deciding here.

**Open question (The interchange conventions carry no gate)** · `open:lint:interchange-gate`

The kickoff states that each of the four disciplines carries its own implementation or adoption gate and that those gates are the linter's real acceptance criteria. Three do; the interchange conventions carry none — the document ends in caveats and references. The gap is harmless if the intended reading is that the interchange duty is discharged by the sibling crate, whose own concept gate, audit, and commissioning have closed, and that the linter's obligation is delegation alone. That reading is what (`conv:lint:gates-as-acceptance`) assumes, and it wants confirming rather than assuming.

**Open question (When the inventory profiles are enabled)** · `open:lint:profile-enablement`

Inventory admits nothing partial: every covered asset carries its derived label at the standard place or the run fails. Both ruled profiles are therefore unsatisfiable the day they are switched on — the test profile's standard place is a generated register that no generator has yet written, and the module profile's place is an inner documentation comment that ~42 definitions lack. The sequencing question is which of three shapes v1 takes: profiles enabled only after the register generator has run once and the module migration has landed; profiles enabled with their findings expected and tracked; or the profile signature staged so that a profile enters only with its migration. The choice determines what the first slice must contain and is not settled by the ratified documents.

**Open question (What a clean run means for v1)** · `open:lint:clean-run-milestone`

Two migrations the architecture already accepted — the ~1210 plain line comments and the ~42 module documentation comments — plus whatever (`open:lint:stray-occurrences`) rules, stand between the linter's first correct run and a corpus-wide exit code of zero. Whether v1's acceptance is a clean run over the whole carrier, or a clean run over the discipline documents and the architecture with the rest carried as known findings against a dated migration plan, decides when the crate can enter CI as a failing gate rather than an advisory one.

**Open question (The partition amendment to the architecture)** · `open:lint:partition-amendment`

The architecture's owner-partition convention still names the Layer 1 interface document among the major documents, while the ruled adoption data places that file outside the carrier entirely — no owner, no prefix. The adoption notes record the amendment and name it a pending edit to the architecture document, taken under the gate clause that admits confirming the convention *as stated or amended*. The edit has not been made. It is one sentence in a document this concept may not edit, and it should land before the architecture's own gate is claimed discharged.

## Concept gate · `sec:lint:gate`

**Gate (Concept review)** · `gate:lint:concept-review`
